# Frontend Fundamentals 모의고사 2회(2603) 복원 Task

## 목표

이미 동작하는 회의실 예약 서비스의 외부 동작을 유지하면서, UI와 코드의 대응 관계, 상태 소유권,
컴포넌트 인터페이스, 서버 상태 흐름을 더 예측 가능한 구조로 리팩터링합니다.

## 먼저 확인할 점

이 문서는 행사에서 배포된 질문 원문이 아닙니다. 현재 직접 확인할 수 있는 공식 자료는
[`requirements.md`](./requirements.md), 시작 코드, 자동화 테스트, Pull Request 템플릿입니다.
행사 안내 페이지의 본문은 현재 공개되지 않아 정확한 문장과 채점 비중은 확인할 수 없습니다.

따라서 아래 Task는 다음 증거를 구분해 복원했습니다.

- **[공식]** 공식 저장소의 요구사항, 코드, 테스트, Pull Request 템플릿에서 직접 확인한 내용
- **[행사 후기]** 참가자가 보존한 행사 안내 문구와 해설 강의 요약에서 교차 확인한 내용
- **[반복 관찰]** 공개 제출 PR의 커밋·본문·리뷰에서 여러 번 나타난 고민
- **[복원 추론]** 위 자료를 실제로 수행할 수 있는 질문 형태로 재구성한 내용

`[반복 관찰]`은 공식 정답이나 평가 기준을 뜻하지 않습니다. 참가자들이 비슷한 문제를 발견했다는
증거일 뿐이며, 서로 다른 구현을 선택한 경우도 많습니다.

## 복원된 과제 문장

> 제공된 회의실 예약 서비스의 기능과 테스트를 유지하면서, 요구사항과 UI가 코드에서 예측 가능하게
> 드러나도록 컴포넌트 책임, 상태와 데이터 흐름, 인터페이스, 코드 배치를 리팩터링하고 그 선택 근거를
> Pull Request에 설명한다.

이 문장은 여러 자료를 종합한 복원 요약이며 공식 원문 인용이 아닙니다.

## 진행 원칙

1. 리팩터링 전에 제품 요구사항과 테스트 결과를 기준선으로 고정합니다.
2. 기존 구현의 모양을 정답으로 가정하지 않고 요구사항과 UI에서 필요한 역할을 먼저 도출합니다.
3. 한 번에 하나의 책임 또는 인터페이스만 바꾸고 관련 테스트를 실행합니다.
4. 파일 수나 줄 수의 감소만으로 추상화가 개선됐다고 판단하지 않습니다.
5. 아래 구현 선택지는 정답으로 복사하지 않고 현재 코드에 맞는 근거를 설명합니다.

## 2. 예약 현황 페이지

### TASK 03. 날짜 선택·예약 현황·내 예약·취소가 한 페이지에 섞여 있을 때 어떤 책임을 경계로 나눠야 할까요?

**근거:** [공식] 화면 구조, [반복 관찰] 컴포넌트 경계·UI/코드 대응 관련 커밋과 PR

**구체적인 요구사항**

- [ ] 페이지에는 날짜 선택 → 현황 확인 → 내 예약 관리 → 예약하기 이동의 흐름이 드러나게 합니다.
- [ ] 날짜 입력은 날짜를 표시하고 변경 의도를 전달하는 책임에 집중합니다.
- [ ] 타임라인은 회의실별 예약 상태와 예약 상세를 표시하는 책임에 집중합니다.
- [ ] 내 예약 영역은 목록 표시와 취소 동작을 응집시킵니다.
- [ ] 추출한 컴포넌트가 페이지의 여러 setter와 내부 상태 구조를 그대로 전달받지 않게 합니다.
- [ ] 단순 JSX 묶음인지, 독립된 책임을 숨기는 추상화인지 구분합니다.

**완료 조건**

- [ ] 실제 화면 순서와 코드의 주요 호출 순서가 대응합니다.
- [ ] 각 컴포넌트의 이름과 공개 인터페이스만 보고 역할을 예측할 수 있습니다.

### TASK 04. 날짜가 바뀔 때 해당 날짜의 예약만 다시 조회하려면 서버 상태의 소유권을 어디에 둬야 할까요?

**근거:** [공식] 날짜 변경 재조회 요구사항, [반복 관찰] query 소유권 관련 커밋·리뷰

**구체적인 요구사항**

- [ ] 선택 날짜가 `GET /api/reservations?date=YYYY-MM-DD`의 명시적인 입력이 되게 합니다.
- [ ] query key 또는 동등한 식별자가 날짜를 포함하도록 합니다.
- [ ] 날짜와 무관한 회의실 목록·내 예약 목록을 불필요하게 다시 요청하지 않습니다.
- [ ] 이전 날짜 요청이 늦게 끝나 현재 날짜 화면을 덮어쓰지 않는지 확인합니다.
- [ ] 조회를 페이지에서 시작할지 실제 소비 컴포넌트 가까이에서 시작할지 판단 근거를 적습니다.

**완료 조건**

- [ ] 날짜를 연속 변경해도 마지막으로 선택한 날짜의 예약만 표시됩니다.
- [ ] 어떤 날짜가 어떤 캐시와 요청을 식별하는지 코드에서 추적할 수 있습니다.

### TASK 05. 서로 독립적인 서버 조회가 Suspense 때문에 순차 실행되는 상황에서는 어떻게 구성해야 할까요?

**근거:** [반복 관찰] 병렬 query·Suspense·waterfall 관련 커밋과 PR 설명

**구체적인 요구사항**

- [ ] 한 컴포넌트에서 여러 Suspense query를 순서대로 호출할 때 실제 시작 시점을 확인합니다.
- [ ] 회의실 목록과 예약 목록처럼 서로 의존하지 않는 요청은 병렬로 시작할 수 있게 합니다.
- [ ] 요청을 상위에서 시작해도 데이터 사용 책임이 무조건 상위로 새지 않게 합니다.
- [ ] 로딩 경계와 오류 경계가 어느 화면 범위를 대체하는지 정의합니다.
- [ ] 라이브러리 교체나 버전 상승을 선택했다면 리팩터링에 반드시 필요한지 별도로 설명합니다.

**완료 조건**

- [ ] 독립 요청 사이에 불필요한 네트워크 waterfall이 없습니다.
- [ ] 로딩·오류 경계가 사용자에게 의미 있는 화면 단위와 일치합니다.

### TASK 06. 타임라인의 시간 계산·배치·팝오버 상태가 섞여 있을 때 무엇을 분리해야 할까요?

- [ ] `HH:mm`을 분으로 바꾸는 계산을 DOM 렌더링과 분리합니다.
- [ ] 시작·종료 시각을 타임라인 위치와 너비로 변환하는 계산을 독립적으로 검증합니다.
- [ ] 시간 헤더, 회의실 행, 예약 블록, 상세 팝오버의 경계를 UI 구조로 설명합니다.

- [ ] 시간 계산을 범용 유틸로 둘지 예약 현황 기능 가까이에 둘지 변경 가능성을 기준으로 판단합니다.

**완료 조건**

### TASK 07. 예약 취소 후 내 예약과 날짜별 예약 현황을 함께 갱신하려면 mutation의 책임을 어떻게 정의해야 할까요?

**근거:** [공식] 취소 확인·양쪽 목록 갱신 요구사항, [반복 관찰] mutation·invalidate 관련 커밋과 리뷰

**구체적인 요구사항**

- [ ] 취소 전에 `정말 취소하시겠습니까?` 확인을 받습니다.
- [ ] 사용자가 거부하면 DELETE 요청이나 낙관적 화면 변경을 하지 않습니다.
- [ ] 확인하면 `DELETE /api/reservations/:id`를 한 번 호출합니다.
- [ ] 취소 성공 후 내 예약 목록과 취소한 날짜의 예약 현황을 모두 갱신합니다.
- [ ] mutation 인수에 `id`만 필요한지, 무효화할 날짜까지 명시해야 하는지 검토합니다.
- [ ] 조회 query와 변경 mutation의 정의·부수 효과를 구분합니다.
- [ ] 요청 중인 항목의 취소 버튼을 비활성화할지 결정하고 중복 DELETE를 막습니다.

**완료 조건**

## 확인된 선택지와 확인되지 않은 정답

다음은 공개 제출에서 실제로 사용된 선택지입니다. 어느 하나도 공식 정답으로 확인되지 않았습니다.

| 문제                     | 공개 제출에서 확인된 선택지                                                           |
| ------------------------ | ------------------------------------------------------------------------------------- |
| URL 필터 상태            | native `URLSearchParams`, 전용 URL 상태 라이브러리, 입력 중간 상태만 로컬 버퍼로 관리 |
| 여러 영역의 상태 전달    | 명시적 props, 제한된 Context, query cache 재사용, render props                        |
| 필터 변경 시 선택 초기화 | 변경 함수에서 명시적 reset, effect로 동기화, `key`로 하위 생명주기 재시작             |
| 서버 조회                | 수동 loading/error 분기, query hook, Suspense query, 상위 병렬 prefetch               |
| 일회성 메시지            | `location.state`, 제한된 Context, toast/flash 계층                                    |
| 계산 로직                | 사용 위치 근처 순수 함수, 기능별 utility, 공통 domain utility                         |
| 폴더 구조                | 페이지별 colocation, 기능별 구조, 일부 shared primitive                               |

선택할 때는 “가장 많이 쓰인 방식”이 아니라 다음 질문으로 판단합니다.

- 이 상태의 원천과 생명주기가 어디인가?
- 호출부가 알아야 할 맥락이 실제로 줄어드는가?
- 제품 요구사항과 화면 구조가 코드에 더 직접적으로 드러나는가?
- 변경 영향과 테스트 범위를 더 좁게 설명할 수 있는가?
- 대안보다 얻는 이득이 추가 추상화 비용보다 큰가?

## 최종 완료 체크리스트

- [ ] 공식 `requirements.md`의 모든 외부 동작을 보존했습니다.
- [ ] easy/hard 테스트가 통과하고, 빌드는 통과하거나 기준선 실패만 남았음을 확인했습니다.
- [ ] 예약 현황과 예약하기 화면의 책임이 페이지 호출부에서 드러납니다.
- [ ] 서버 상태, URL 상태, 입력 중간 상태, 파생 계산, 일시적 UI 상태의 소유권이 명확합니다.
- [ ] URL 공유·새로고침·뒤로가기에서 필터 상태가 일치합니다.
- [ ] 시간 충돌·장비·인원·층 필터의 경계 동작이 유지됩니다.
- [ ] 예약 생성과 취소의 성공·실패·pending 상태가 일관됩니다.
- [ ] query와 mutation의 책임, 캐시 식별자, 무효화 범위가 추적 가능합니다.
- [ ] 컴포넌트 인터페이스가 부모의 내부 상태 구현을 불필요하게 노출하지 않습니다.
- [ ] 추출한 코드가 파일 수가 아니라 예측 가능성과 변경 범위를 개선합니다.
- [ ] Pull Request에 문제, 선택 근거, 대안, 검증 결과, 남은 한계를 기록했습니다.
