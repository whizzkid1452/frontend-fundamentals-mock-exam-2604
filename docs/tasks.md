# Frontend Fundamentals 모의고사 2회 예상 Task 목록

## 목표

이미 동작하는 회의실 예약 서비스의 외부 동작을 유지하면서, 약 700줄에 걸쳐 섞여 있는 UI, 서버 상태, 입력 상태, 계산, 오류 처리의 책임을 점진적으로 리팩터링합니다.

## 문서의 성격

- 이 목록은 행사에서 전달된 공식 리팩터링 지시문의 원문이 아닙니다.
- 보존해야 하는 제품 동작은 공식 [`requirements.md`](./requirements.md)와 저장소의 자동화 테스트에서 직접 확인했습니다.
- 컴포넌트 경계, 상태 소유권, 코드 배치에 관한 질문은 공식 PR 템플릿과 공개 해설 후기를 바탕으로 만든 **예상 Task**입니다.
- 복원 근거와 불확실성은 [`../ASSIGNMENT_RECONSTRUCTION.md`](../ASSIGNMENT_RECONSTRUCTION.md)를 참고해주세요.

## 진행 원칙

1. 리팩터링 전 `yarn test`와 `yarn build` 결과를 기준 상태로 기록합니다.
2. 한 Task에서는 한 가지 책임만 이동하거나 개선합니다.
3. 각 Task가 끝날 때 관련 테스트와 전체 테스트를 실행합니다.
4. 파일 수나 줄 수가 줄었다는 이유만으로 완료로 판단하지 않습니다.
5. 호출부가 제품 요구사항을 더 명확하게 표현하고, 변경 영향 범위가 좁아졌는지 확인합니다.

## 기준 동작 확인 Task

### TASK 00. 이미 동작하는 코드를 수정하기 전에 어떤 동작을 기준선으로 고정해야 할까요?

**근거 수준:** 공식 저장소의 테스트와 행사 안내에서 직접 확인

**구체적인 요구사항**

- [ ] `yarn test`를 실행해 기존 테스트 결과를 기록합니다.
- [ ] `yarn build`를 실행해 TypeScript 검사와 프로덕션 빌드 결과를 기록합니다.
- [ ] `/`와 `/booking`의 핵심 사용자 흐름을 브라우저에서 확인합니다.
- [ ] `docs/requirements.md`의 각 요구사항과 이를 검증하는 테스트를 연결합니다.
- [ ] 테스트가 검증하지 않는 메시지, 로딩 상태, URL 복원 동작도 수동 체크리스트로 남깁니다.

**완료 조건**

- [ ] 리팩터링 전후를 비교할 수 있는 테스트 결과와 사용자 동작 목록이 있습니다.
- [ ] 기존에 이미 실패하던 항목과 리팩터링으로 새로 실패한 항목을 구분할 수 있습니다.

### TASK 01. 기존 구현을 그대로 따라가지 않고 화면의 역할부터 다시 정의해야 하는 상황에서는 어떻게 시작해야 할까요?

**근거 수준:** 공개 해설에서 반복적으로 확인된 리팩터링 관점

**구체적인 요구사항**

- [ ] 예약 현황 페이지를 날짜 선택, 타임라인, 내 예약 목록, 이동 동작으로 나눠 적습니다.
- [ ] 예약하기 페이지를 조건 입력, 유효성 검증, 예약 가능 목록, 예약 확정으로 나눠 적습니다.
- [ ] 각 영역이 필요로 하는 값과 사용자 이벤트를 기존 구현과 무관하게 먼저 정의합니다.
- [ ] 서버 데이터, 사용자 입력, 입력에서 계산되는 파생 값을 구분합니다.
- [ ] 어떤 상태를 어느 컴포넌트가 소유해야 하는지 근거를 적습니다.

**완료 조건**

- [ ] 화면에서 보이는 각 책임을 코드에서 어디에서 찾을 수 있어야 하는지 설명할 수 있습니다.
- [ ] 파일 분리 계획이 아니라 역할과 인터페이스 계획이 먼저 작성되어 있습니다.

## 예약 현황 페이지 리팩터링 Task

### TASK 02. 날짜 변경·예약 현황·내 예약·취소 로직이 한 페이지에 모인 상황에서는 컴포넌트 책임을 어떻게 분리해야 할까요?

**근거 수준:** 시작 코드에서 직접 확인한 구조와 공개 해설을 결합한 예상 Task

**구체적인 요구사항**

- [ ] 페이지는 선택 날짜와 화면 영역의 조립 관계를 읽을 수 있게 유지합니다.
- [ ] 날짜 입력은 `value`와 `onChange`처럼 역할이 드러나는 인터페이스를 사용합니다.
- [ ] 타임라인은 예약 데이터와 선택 이벤트를 받아 표시하는 책임에 집중합니다.
- [ ] 내 예약 목록은 표시와 취소 요청 의도를 부모에게 전달하는 책임에 집중합니다.
- [ ] 추출된 컴포넌트가 페이지의 여러 setter를 직접 전달받지 않게 합니다.

**완료 조건**

- [ ] 날짜 선택, 타임라인, 내 예약 목록의 코드를 화면 구조와 같은 순서로 찾을 수 있습니다.
- [ ] 각 컴포넌트의 공개 속성만 보고 역할과 이벤트를 이해할 수 있습니다.

### TASK 03. 날짜가 바뀔 때 해당 날짜의 예약만 다시 가져와야 하는 상황에서는 서버 상태 흐름을 어떻게 표현해야 할까요?

**근거 수준:** 공식 요구사항과 자동화 테스트에서 직접 확인

**구체적인 요구사항**

- [ ] 선택 날짜가 예약 현황 요청의 명시적인 입력이 되게 합니다.
- [ ] 날짜가 바뀌면 `GET /api/reservations?date=YYYY-MM-DD`를 새 날짜로 호출합니다.
- [ ] 회의실 목록과 내 예약 목록처럼 날짜와 무관한 요청을 불필요하게 반복하지 않습니다.
- [ ] 이전 날짜 요청이 늦게 완료되는 경우 현재 날짜 화면을 덮어쓸 가능성을 검토합니다.
- [ ] 요청 중·실패·성공 상태의 소유 위치를 일관되게 정합니다.

**완료 조건**

- [ ] 날짜를 연속으로 변경해도 마지막으로 선택한 날짜의 예약만 표시됩니다.
- [ ] 어떤 사용자 동작이 어떤 API 재요청을 발생시키는지 호출부에서 추적할 수 있습니다.

### TASK 04. 타임라인 위치 계산과 예약 상세 팝오버 렌더링이 섞여 있는 상황에서는 무엇을 분리해야 할까요?

**근거 수준:** 공식 요구사항과 시작 코드에서 직접 확인한 구조

**구체적인 요구사항**

- [ ] `09:00~20:00` 범위와 30분 간격을 이름 있는 상수로 표현합니다.
- [ ] `HH:mm`을 분 단위로 바꾸는 계산을 DOM 렌더링과 분리합니다.
- [ ] 예약 시작 시각과 종료 시각을 타임라인의 위치와 너비로 변환하는 계산을 독립적으로 검증합니다.
- [ ] 예약 블록 선택 상태는 예약 `id`를 기준으로 관리합니다.
- [ ] 선택된 예약의 시간, 인원, 장비를 팝오버에 표시합니다.

**완료 조건**

- [ ] 09:00 시작, 20:00 종료, 30분 예약의 경계 위치를 DOM 없이 검증할 수 있습니다.
- [ ] 타임라인 표시 방법을 바꿔도 시간 변환 규칙을 다시 작성하지 않습니다.

### TASK 05. 예약 취소 후 내 예약 목록과 예약 현황이 함께 바뀌어야 하는 상황에서는 어떻게 일관성을 유지해야 할까요?

**근거 수준:** 공식 요구사항과 자동화 테스트에서 직접 확인

**구체적인 요구사항**

- [ ] 취소 전에 `정말 취소하시겠습니까?` 확인을 받습니다.
- [ ] 사용자가 거부하면 DELETE 요청과 화면 갱신을 수행하지 않습니다.
- [ ] 확인하면 `DELETE /api/reservations/:id`를 호출합니다.
- [ ] 성공 후 내 예약 목록과 현재 날짜 예약 현황을 모두 갱신합니다.
- [ ] 실패하면 성공 상태로 보이는 부분 업데이트를 남기지 않고 오류를 표시합니다.

**완료 조건**

- [ ] 취소 성공 직후 두 화면 영역에서 같은 예약이 사라집니다.
- [ ] 취소 거부와 실패 경로에서 서버 및 화면 상태가 요구사항과 일치합니다.

## 예약하기 페이지 리팩터링 Task

### TASK 06. URL 쿼리와 로컬 상태가 같은 필터 값을 각각 보관하는 상황에서는 진실 공급원을 어떻게 정해야 할까요?

**근거 수준:** 공식 URL 공유 요구사항과 시작 코드에서 직접 확인한 중복 상태

**구체적인 요구사항**

- [ ] 날짜, 시작·종료 시간, 참석 인원, 장비, 선호 층의 정규 형태를 정의합니다.
- [ ] URL을 직접 열었을 때 쿼리 값으로 필터가 복원됩니다.
- [ ] 필터를 변경하면 URL 쿼리가 현재 값을 반영합니다.
- [ ] 브라우저 뒤로가기·앞으로가기 시 URL과 화면 입력값이 어긋나지 않는지 확인합니다.
- [ ] 잘못된 쿼리 값에 대한 기본값과 정규화 규칙을 정의합니다.
- [ ] URL과 로컬 상태 중 어느 쪽이 기준인지 코드에서 분명하게 드러냅니다.

**완료 조건**

- [ ] URL을 복사해 새 탭에서 열어도 같은 필터가 표시됩니다.
- [ ] 같은 값을 동기화하기 위한 효과가 순환 업데이트를 만들지 않습니다.

### TASK 07. 시간과 참석 인원 입력이 미완성이거나 유효하지 않은 상황에서는 검증 결과를 어떻게 표현해야 할까요?

**근거 수준:** 공식 요구사항과 자동화 테스트에서 직접 확인

**구체적인 요구사항**

- [ ] 날짜는 오늘 이후만 허용합니다.
- [ ] 시작 시간은 09:00~19:30, 종료 시간은 09:30~20:00 범위에서 선택합니다.
- [ ] 종료 시간은 시작 시간보다 늦어야 합니다.
- [ ] 참석 인원은 1명 이상이어야 합니다.
- [ ] 시간 조건이 미완성이거나 오류가 있으면 예약 가능 목록을 표시하지 않습니다.
- [ ] 검증 결과를 별도의 동기화된 상태로 복제하기보다 현재 입력에서 계산할 수 있는지 검토합니다.

**완료 조건**

- [ ] 시작 10:00·종료 10:00, 시작 10:30·종료 10:00이 모두 거부됩니다.
- [ ] 오류를 수정하면 오래된 오류 메시지 없이 목록이 다시 계산됩니다.

### TASK 08. 참석 인원·장비·층·기존 예약을 모두 고려해야 하는 상황에서는 예약 가능 회의실을 어떻게 계산해야 할까요?

**근거 수준:** 공식 요구사항에서 직접 확인

**구체적인 요구사항**

- [ ] `room.capacity >= attendees`인 회의실만 포함합니다.
- [ ] 사용자가 선택한 모든 장비가 `room.equipment`에 포함되어야 합니다.
- [ ] 선호 층이 있으면 `room.floor === preferredFloor`를 적용합니다.
- [ ] 선호 층이 없으면 모든 층을 후보로 둡니다.
- [ ] 같은 날짜·같은 회의실에서 `[start, end)`가 기존 예약과 겹치지 않아야 합니다.
- [ ] 필터 결과는 층 오름차순, 같은 층에서는 이름순으로 정렬합니다.

**완료 조건**

- [ ] 기존 예약이 10:00~11:00이면 09:30~10:00과 11:00~11:30은 충돌하지 않습니다.
- [ ] 선택 장비가 두 개라면 둘 중 하나만 가진 회의실은 제외됩니다.
- [ ] 필터와 정렬 계산을 React 렌더링 없이 검증할 수 있습니다.

### TASK 09. 필터를 바꾼 뒤 이전에 선택한 회의실이 더 이상 예약 가능하지 않은 상황에서는 어떻게 처리해야 할까요?

**근거 수준:** 공식 요구사항에서 직접 확인

**구체적인 요구사항**

- [ ] 날짜, 시간, 인원, 장비, 층 중 하나가 바뀌면 선택한 회의실을 초기화합니다.
- [ ] 이전 예약 실패 메시지도 함께 초기화합니다.
- [ ] 입력 변경 처리마다 같은 초기화 코드를 복사하지 않습니다.
- [ ] 초기화 시점이 필터 상태 변경보다 한 이벤트 늦어지지 않게 합니다.

**완료 조건**

- [ ] 회의실 선택 후 어떤 필터든 변경하면 선택 표시와 오류 메시지가 즉시 사라집니다.
- [ ] 새 조건으로 예약할 때 이전 `roomId`가 요청에 포함되지 않습니다.

### TASK 10. 예약 버튼을 빠르게 여러 번 누르거나 서버가 실패하는 상황에서는 비동기 상태를 어떻게 관리해야 할까요?

**근거 수준:** 공식 성공·실패·로딩 요구사항에서 직접 확인

**구체적인 요구사항**

- [ ] 회의실 미선택과 유효하지 않은 시간은 API 호출 전에 차단합니다.
- [ ] 요청 중 버튼을 비활성화하고 `예약 중...`을 표시합니다.
- [ ] 같은 사용자 동작으로 중복 POST 요청이 발생하지 않게 합니다.
- [ ] 성공하면 성공 메시지를 표시하고 `/`로 이동합니다.
- [ ] 성공 후 해당 날짜의 예약 현황이 다시 조회되게 합니다.
- [ ] 실패하면 서버 메시지를 표시하고 선택 회의실을 초기화합니다.
- [ ] 성공·실패 어느 경로에서도 요청 중 상태가 남지 않게 합니다.

**완료 조건**

- [ ] 연속 클릭에도 예약 생성 요청은 한 번만 처리됩니다.
- [ ] `CONFLICT`, `INVALID`, `NOT_FOUND` 실패 후 사용자가 조건을 수정해 다시 시도할 수 있습니다.

## 인터페이스와 코드 배치 Task

### TASK 11. 하위 컴포넌트가 부모의 `setState` 구현을 그대로 전달받는 상황에서는 인터페이스를 어떻게 바꿔야 할까요?

**근거 수준:** 공개 해설에서 반복적으로 확인된 리팩터링 관점

**구체적인 요구사항**

- [ ] `setDate`보다 `value`와 `onChange`처럼 컴포넌트 역할을 나타내는 이름을 사용합니다.
- [ ] 하위 컴포넌트가 부모 상태의 전체 형태를 변경할 수 없게 필요한 이벤트만 노출합니다.
- [ ] 이벤트 인수는 DOM 이벤트보다 제품 의미가 있는 값으로 전달할지 검토합니다.
- [ ] 읽기 전용 표시 컴포넌트에는 상태 변경 함수를 전달하지 않습니다.
- [ ] 인터페이스만 보고 필수 입력과 선택 입력을 구분할 수 있게 타입을 정의합니다.

**완료 조건**

- [ ] 부모의 상태 관리 방법을 바꿔도 하위 컴포넌트의 공개 인터페이스가 불필요하게 바뀌지 않습니다.
- [ ] 호출부가 화면에서 일어나는 사용자 동작을 직접 읽히게 표현합니다.

### TASK 12. 코드를 여러 파일로 옮겼지만 이해하려면 계속 파일을 왕복해야 하는 상황에서는 어떻게 개선해야 할까요?

**근거 수준:** 공개 해설에서 반복적으로 확인된 코드 배치 관점

**구체적인 요구사항**

- [ ] 한 번만 사용되고 짧은 코드는 사용하는 화면 영역 가까이에 둡니다.
- [ ] 여러 영역에서 공유하거나 독립적으로 검증할 가치가 있는 로직만 별도 모듈로 이동합니다.
- [ ] 추출한 이름이 `어떻게`가 아니라 `무엇`을 수행하는지 드러내게 합니다.
- [ ] 호출부가 알 필요 없는 시간 계산, API 세부사항, 상태 전이를 내부에 숨깁니다.
- [ ] 순환 의존성이나 페이지 간 역방향 의존성을 만들지 않습니다.

**완료 조건**

- [ ] 화면의 한 기능을 이해하기 위해 열어야 하는 파일과 기억해야 하는 상태가 실제로 줄어듭니다.
- [ ] 파일 수 증가가 아니라 호출부의 인지 부담 감소로 추상화의 효과를 설명할 수 있습니다.

### TASK 13. 두 페이지에서 날짜·시간·장비 표현이 반복되는 상황에서는 무엇을 공유해야 할까요?

**근거 수준:** 시작 코드의 중복에서 도출한 예상 Task

**구체적인 요구사항**

- [ ] 같은 도메인 규칙인지, 우연히 현재 구현만 비슷한지 먼저 구분합니다.
- [ ] 장비 코드와 사용자 표시명처럼 의미가 동일한 데이터는 하나의 정의로 관리할지 검토합니다.
- [ ] 날짜 포맷과 시간 슬롯 생성처럼 규칙이 동일한 계산은 중복 동작 테스트로 확인합니다.
- [ ] 페이지별 요구가 달라질 가능성이 높은 UI 마크업은 성급하게 하나로 합치지 않습니다.
- [ ] 공유 모듈이 두 페이지의 내부 상태 타입에 의존하지 않게 합니다.

**완료 조건**

- [ ] 같은 규칙을 변경할 때 서로 다른 파일을 따로 수정해 결과가 어긋날 가능성이 줄어듭니다.
- [ ] 공유하지 않기로 한 코드에는 페이지별 변경 가능성이라는 설명 가능한 근거가 있습니다.
